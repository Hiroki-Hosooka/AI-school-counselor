# トップ画面とインテークの見直し

## 0. 前提

### 0-1 この指示書の位置づけ

- `fix-after-shima4.md` の**第5部(トップ画面)は、この指示書で置き換える**。第5部は実装しなくてよい
- `fix-after-shima4.md` の第1部(不具合)と並行して進めてよい。ただし、チップの選択の受け取り(第1部 1-1)と、この指示書の3章は同じ仕組みに関わるので、一つの設計にまとめること
- 設計→私の確認→実装→検証、の順で進める。設計を見せるまで実装しない

### 0-2 参照するもの

- モックアップ:`docs/design/top-screen/Main.dc.html`(タブレット・PC)、`Phone.dc.html`(スマホ)、`Details.dc.html`(「くわしく」)。見た目の参考で、そのまま使うコードではない
- 嶋先生とのミーティング(10/14)の文字起こし:`docs/interviews/2026-10-14-shima-4-transcript.md`

### 0-3 なぜ変えるか

- 今のトップ画面は、文字が薄くて小さく、最初に何をすればいいかわからない(ミーティングでの指摘)
- 書き出しの例(「全部あの子のせいだと思う」など)が具体的すぎて、相談者の攻撃的な気持ちを刺激した(嶋先生)
- 自由に書いたあと、AIが文章の中に番号つきの選択肢を並べ、相談者が「1と4」と数字を打つ形になっていた。入り口の印象とずれるうえ、インテークの記録も不安定
- 内部の判定(重心・関わりの型など)が、生徒の画面に表示されている
- **チップを押してもインテークに進む時と進まない時があり、再現性がない。** 研究として不十分

## 1. 最初の画面

### 1-1 見出し

- 見出しを次の2行にする。どちらも見出しの一部として、読める大きさと濃さにする
  - 1行目:よくぞ来てくれました。
  - 2行目:今日は、どんなことで来てくれた?
- 「話したいことから、どこからでもどうぞ。」と、「書き出しに迷ったら」と書き出しの例のチップは**削除する**
- **タイトル(相談室)の直下に説明文を置かない**
- 「よくぞ来てくれました」は、嶋先生が「入り口がすごく優しい」と評価した言葉なので残す

### 1-2 選択肢

見出しのすぐ下に、次の6つのボタンを、画面の主役として大きく置く。

| ボタンの文字 | 記録する主訴 | 意味 |
|---|---|---|
| 友達・人間関係 | 1 | |
| 勉強・進路・部活 | 2 | |
| 家族・家のこと | 3 | |
| 自分の気持ちや性格 | 4 | |
| うまく言えない | 5 | なんとなくしんどくて、言葉にならない人 |
| どれに当てはまるかわからない | 未分類(新しい値) | 話したいことはあるが、どの分類にも当てはまらない人 |

- 「未分類」を記録するために DB の変更が必要なら、SQL を用意すること(Supabase での実行は私が行う)
- タブレット・PCでは横に並べて折り返す。スマホでは縦に並べる
- 押す部分の高さは44px以上

### 1-3 書く欄

- 選択肢の下に「あてはまるものがなければ、そのまま書いてもいいよ。」と書き、その下に書く欄と「送る」ボタンを置く
- 何も話していない最初の状態だけ、この位置に置く。会話が始まったら、ふつうのチャットと同じく画面の下に移す

### 1-4 画面の下

- 「相手はAIです。話したことは記録されます。」と「くわしく」のリンク
- 「いますぐ助けが必要なとき」と、119番、24時間子供SOSダイヤル(0120-0-78310)。電話番号は押せばかけられるリンクにする
- 読める大きさ(14px以上)と濃さで、会話中も常に見える位置に置く
- 「くわしく」を押すと、`Details.dc.html` の内容を表示する
  - **「心理の専門家が読むことがあります」「学校の先生に知らせが届きます」は、学校との取り決めがまだなので仮の文面**。定数にまとめ、差し替えやすくしておく

### 1-5 生徒の画面から外すもの

- 4つの円(関係・主訴・目標・作戦会議)
- 「いまの重心」「関わりの型」
- 「接続済み」「設定と記録」
- 返事ごとの「この返答の評価 1〜5」

開発用の表示は、環境変数などで有効にしたときだけ出す。**本番では必ず出さない。** どの設定で出し入れするかを、設計で示すこと。

### 1-6 見た目の決まり

- 文字と背景の色の差は4.5対1以上
- 色と書体は今のアプリ(藍色 #2F4858、明朝体の見出し、ゴシック体の本文)に合わせる
- 学校のタブレット、Chromebook、スマホの大きさで崩れないこと

## 2. インテークの流れ

### 2-1 全体

| ターン | 聞くこと | 形 | 誰が決めるか |
|---|---|---|---|
| 1 | 主訴 | 最初の画面の選択肢(1-2) | **コード** |
| 2 | きっかけ・背景 | AIが言葉で聞く。相談者は自由に書く | AIは問いの言葉だけ |
| 3 | つらさ | 1〜5のチップ | **コード** |
| 4 | なりたい姿 | チップ | **コード** |

### 2-2 選択肢を押した場合

- 押した選択肢の文字を、相談者の最初の発言として表示する
- 主訴を、**コードで確実に記録する**(AIの判断を通さない)
- AIの最初の返事は、主訴を聞き直さず、2ターン目(きっかけ・背景)から始める
- 「うまく言えない」の場合は、きっかけを急かさない。石田先生の「そっか、わかんないかー。話したかったら話してもいいし、別の話題でもいいし」(ナレッジ V6)の姿勢で聞く
- 「どれに当てはまるかわからない」の場合は、どんなことかを自由に書いてもらう問いにする

### 2-3 選択肢を押さずに書いた場合

ミーティングで、「話したいことが決まっているのに数字で選べと言われたら、うざい」という意見が出た。

- 主訴を**聞き直さない**。番号つきの選択肢も、主訴を確かめるチップも出さない
- AIが書かれた内容から主訴を推定して記録する。記録には、選択肢から来たのか、AIの推定なのかを区別する印を付ける(研究のため)
- 書かれた内容に、きっかけ・背景がすでに含まれていれば、2ターン目は飛ばしてよい

### 2-4 つらさとなりたい姿のチップ

- 文章の中に番号つきの選択肢を並べる形は、**すべてやめる**
- つらさ(仮):1 少し気になる/2 まあまあモヤモヤする/3 かなりつらい/4 限界に近い/5 もう耐えられない
  - **危機のときの気持ちのスケーリングも、このラベルにそろえる**(今は「4 かなりつらい」と「4: 限界に近い」が混在している)
- なりたい姿(仮):吐き出したい/一緒に整理したい/どっちも/まだわからない
- どちらも、数字や言葉を手で打っても、チップを押したのと同じに扱う
- チップの前に、短い受け止めの一言を置く(問いだけを続けて並べない)

### 2-5 チップの連続について

これまで「2回続けてチップを出さない」と決めていたが、**インテークの3ターン目と4ターン目は例外**とする。嶋先生が感じた「作業感」を減らすため、次を守ること。

- 3と4のあいだに、相談者の答えへの短い受け止めを挟む
- インテークの外では、これまでどおり2回続けない

### 2-6 インテークの答えを危機の判定にかけない

- インテークの答え(選択肢・数字)とチップの選択は、危機の判定の対象にしない(`fix-after-shima4.md` 1-2 と同じ)
- つらさが4・5の場合は、これまでどおりインテークの決まり(人への相談を促す流れ)で扱う
- 2ターン目の自由記述は、これまでどおり判定にかける

## 3. 再現性:流れはコードで決める

### 3-1 考え方

再現性がないことには、性質の違う2種類がある。

| 種類 | 例 | 目標 |
|---|---|---|
| 流れ | チップを押したらインテークに進む、どのターンで何を聞くか | **毎回同じ。揺れたら不具合** |
| 生成と曖昧な判定 | 返事の言葉、曖昧な発言の危機の判定 | 揺れは避けられない。小さくし、測って報告する |

**流れに関わる判断は、すべてコードの状態の流れで決め、AIには任せない。** AIに任せるのは、決められた場面で何と言うか(言葉)だけにする。

### 3-2 やること

1. **今、流れの判断のうちAIに任せている部分を、すべて洗い出して報告する。** たとえば、次に何を聞くかをAIの出力(JSON の値など)で決めている箇所、インテークが終わったかをAIが判断している箇所
2. インテークの4つのターンの進み方を、コードの状態として持つ(今どのターンか、何が記録済みか)
3. 洗い出した部分のうち、インテークに関わるものは、この作業でコードに移す。それ以外(危機の流れなど)は、移す案を出すところまで

### 3-3 記録

研究のため、会話の1ターンごとに次を記録する。すでに記録しているものは、そのままでよい。

- 使ったモデルの名前(版が決まった名前。「最新版」を指す名前は使わない)
- プロンプトの版
- ナレッジの版(件数・更新日)
- 設定(段階ごとの応答が有効か、など)
- インテークのどのターンか、主訴の記録の出どころ(選択肢/AIの推定)

## 4. 検証

### 4-1 流れの再現性(無料枠)

- 6つの選択肢それぞれについて、押した操作を**5回ずつ**、画面の操作と同じ API の経路で流す
- 次がすべて**30回中30回**であること
  - 主訴が正しく記録される
  - AIの最初の返事が、主訴を聞き直さずに2ターン目に進む
  - 危機の判定にかけられない
- つらさ・なりたい姿のチップを押した操作と、同じ数字や言葉を手で打った操作の両方で、同じように記録されること

### 4-2 自由記述の場合

- 選択肢を押さずに書いた場合(短い文・長い文・すでに背景を含む文)を流し、主訴を聞き直さないこと、推定の印が付くことを確かめる

### 4-3 見た目

- タブレット(縦・横)、Chromebook、スマホの大きさで、画面のスクリーンショットを撮って見せる
- 本番の設定で、1-5の表示が出ていないことを確かめる

---

## 5. 守ること

- 流れの判断をAIに任せない
- 本番で開発用の表示を出さない
- 画面下の窓口の表示を、どの状態でも消さない
- 「くわしく」の仮の文面は、学校との取り決めのあとに確定する
- 採用したら、CLAUDE.md に次を書き足す
  - インテークの1ターン目は最初の画面の選択肢で行い、コードで記録する
  - 流れの判断はコードで決め、AIは言葉だけを担う
  - 1ターンごとに、モデル・プロンプト・ナレッジの版を記録する
