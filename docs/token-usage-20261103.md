人の指示「11/1 に本人の危機のターンを強く縛った生成に替えてから、トークン数が大きく増えた」を受けて、(1) 測る仕組みを入れて測り、

## 0. 要点

- **1ターンあたり 約1.6円(約$0.011)**。会話あたりは 4ターンで約5〜7円、10〜14ターンで約20円、31ターン(55932e90)で約55円(見積もり。2章)。
- 内訳: **生成の入力 48%**(フェーズ2のシステムプロンプトが 約7,600〜8,300トークン)、**危機の分類器 36%(そのうち思考だけで全体の 30%)**、
  生成の出力 10%、作り直し 5%、人単位のメモ 1%未満。
- 11/1 の「危機のターンを生成に」で増えたのは、危機のターン1回につき生成1回(約1.2円)分。危機のある会話で1〜2回なので、**会話全体の 5〜10% 程度**。
  増えた感じの主な原因は、それより前からある**分類器の思考トークン**と、**フェーズ2のプロンプトの大きさ**(11/1 で生成のシステムプロンプトは約7%、
  分類器のプロンプトは約18%大きくなった)だと考えられる(4-3節)。
- 効果の大きい案: ① 分類器の思考を止める(全体の **約-30%**。4文の試しでは思考0・判定は同じ)、② 変わらない部分を先頭に集めて暗黙のキャッシュを効かせる
  (**-15%前後**、上限で -30%)、③ 場面ごとにフェーズ2の指示を組む(**-6〜8%**)。①②で全体の **約4割減** の見込み。
- **危機の分類器は本当に「2回並行」**(既定 2回・同時に送り、本人の危機が1回でも返ればもう1回を待たずに確定。待たなかった回も課金される)。
  2回の判定が食い違った割合は **3.2〜10.8%**。向きのほとんどは **none と watch**(段階0と1の境目)。段階2になるかが片方の判定だけで決まった
  (キーワード・受動パターンが無く、本人の危機が1回だけ)のは **0.5〜2.0%** で、**正解のラベルは「虐待」が3件・誤検知の確認の文が1件**。
  思考を止めたあとは、1回にしても全体の約4%しか減らないので、**2回のまま**を勧める(3章)。

## 3. 危機の分類器の2回並行の判定(変えていない)

### 3-1. コードで確かめたこと

- `src/classify.mjs` の `classifierVotes()` が既定 **2**(設定 `CRISIS_CLASSIFIER_VOTES` で 1〜3)。`runVotes` が **同時に** n 回送る(並行)。
- 1回でも本人の危機(crisis・self)が返ったら、残りを待たずに段階2で確定する(待ち時間を伸ばさないため)。**待たなかった回も Google 側では処理・課金される**。
- どちらか1回でも本人の危機(根拠の引用が今の発言にあるもの)なら段階2。watch が1回でもあれば段階1。1回が失敗しても、もう1回の判定が使われる
  (両方失敗したら段階1)。本人か第三者かは、判定できた回がすべて other のときだけ第三者。
- 判定の前に、キーワード・受動パターンの照合(段階2を強制)と、中身の無い短い返事の除外(分類器にかけない)がある。

### 3-2. 食い違った割合と向き(`node scripts/analyze-classifier-votes.mjs`)

| データ | 2回とも判定できた | risk の食い違い | 向き(組み合わせ) | 段階2が片方だけで決まった(キーワード・受動パターン無し) |
|---|---|---|---|---|
| 開発用の文(危機の引用の確かめ。11/1) | 147 | **8(5.4%)** | none+watch 6・none+crisis 1・watch+crisis 1 | 3(2.0%)。正解: 虐待 2・誤検知の確認 1 |
| 開発用の文(キーワード v3。10/9) | 220 | **7(3.2%)** | none+watch 7 | 1(0.5%)。正解: 虐待 1 |
| 今回のログの再生(10/28・11/03) | 65 | **7(10.8%)** | none+watch 6・watch+crisis 1 | 1(1.5%)。「あしらわれたら立ち直れない」(引用の確かめで段階1に) |

- subject(本人か第三者か)の食い違いは 0〜1.4%。
- **食い違いのほとんどは none と watch(段階0と1の境目)**。1回だけにすると、この境目がその回しだいになる(段階1は生成の指示が変わるだけで、通知は出ない)。
- **重いほうの食い違い(片方だけ crisis)は 0.5〜2%で、その多くがキーワードの無い虐待の打ち明け**。1回にすると、これがほぼ半分の確率で段階1にとどまり、
  職員への通知が出ない。
- 過去の開発用の結果では、**片方の回だけが失敗(無料枠の混雑)した判定が 47〜57%** あった(両方失敗は 0)。2回並行は、失敗への備えとしても効いている
  (1回にすると、失敗したときは段階1止まりになる)。有料枠の本番での失敗率は、`timings.tokens.by.classifier` の `n` と `ok` の差で測れるようになった。
- 保留セットの結果は読んでいない(決まりのとおり)。

### 3-3. 勧め

**2回のままにする。** いまの費用では1回にすると全体の約18%減るが、案①(思考を止める)を入れたあとは、分類器の費用は全体の約8%になり、1回にしても
**約4%しか減らない**。減る額に比べて、キーワードの無い虐待の打ち明けを段階1に落とす危険が大きい。変えるなら、案①のあとに、上の食い違いを本番の記録でも
測ってから(人が決める)。

## 4. 減らす案(効果の大きい順。どれもまだ入れていない)

割合は、2-4節の6会話の合計(約120円)に対する見込み。

| 順 | 案 | 見込み | 危険・確かめること |
|---|---|---|---|
| ① | **分類器・補助判定・人単位のメモの思考を止める**(lite に `thinkingBudget` の上限(例 128〜512)か `thinkingLevel: "low"` を渡す。いまは -1 = 動的) | **約-30%**(分類器の費用が 約43円 → 約7円) | 判定の精度が変わりうる。試した4文(`docs/test-results/token-usage-20261103-thinking-probe.txt`)では、どの設定でも思考 0・判定は同じだった。**以前「lite は 0 を受け付けない」とわかっていたが、128・512・thinkingLevel は受け付けた**。予備の 3.1-flash-lite は試していない。入れる前に、開発用の文と保留セットで、明示的な危機の表現の見逃し 0・Tier A の見逃しが増えない・none が段階2が増えないことを確かめる(5章) |

### 4-1. 11/1 の変更でどれだけ増えたか(わかった範囲)

- 本番の既定で、本人の危機のターンが固定の文(0トークン)から生成(フェーズ2なら 約1.2円・インテーク中なら 約0.6円)になった。今回のログでは危機のターンは
  会話ごとに1〜2回なので、**+1〜2.5円/会話(会話全体の 5〜10% 程度)**。生成のあとの確かめ(危機の出力チェック・問いで終えるかの確かめ)に当たると、作り直しがもう1回増える。
- 同じ台本を模擬の返事で流して比べると、**生成のシステムプロンプトは 平均11,422字 → 12,201字(+7%)、分類器のプロンプトは 1,227字 → 1,446字(+18%。根拠の引用の決まり)**
  (前の版は 11/1 の作り直しの前のコミット d5e0890)。
- 冒頭の言い直しの作り直し(11/1 g)は、返事が言い直しを続けると作り直しが増える仕組み。本番の割合は `regen_flow` で見る。

## 5. 費用の上限の案(人が決める)

数字はすべて仮。上限で止めるときも、**危機の分岐(キーワード・受動パターンの照合・危機の応答・職員への通知・画面の下の窓口)は止めない**
(CLAUDE.md 5.2 の「字数・回数の上限を超えた発言でも、この分岐は外さない」と同じ考え方。`classifyLocal` を使う)。

| | 上限(仮) | 近づいたとき | 超えたとき |
|---|---|---|---|
| 1回の会話 | 60往復 または 100円相当のトークン(`timings.tokens` の会話ごとの合計) | 生徒の画面には出さない。管理画面の会話の一覧に印 | 生徒向けの一言(仮・心理士の確認待ち。例「今日はたくさん話してくれたね。続きは、少し時間をおいてからでも大丈夫だよ」+画面の下の窓口)で新しい会話をすすめる。危機の分岐は今までどおり |
| 1日(全体) | 例 3,000円/日(1日100会話の見込みの約1.5倍) | 70%: 管理画面の上に行・職員の通知先に「費用が70%」(相談の本文・セッションIDは送らない。5.3) | 90%: 新しい会話にだけ控えめなお知らせ。100%: 新しい会話の生成を止め、お知らせ+窓口。続いている会話と危機の分岐は止めない |
| 外側の備え | Google Cloud の予算アラート(有料のプロジェクト) | 50%・90% でメール | 自動では止まらない(止める仕組みはこちらで持つ) |

- いまある上限: 1人1時間 60回(`RATE_LIMIT_PER_HOUR`)・1回 2,000字。
- 1日の合計は、`messages.timings.tokens` を SQL で合計する(db/schema.sql 17節)。サーバで毎ターン数えると重いので、数分ごとの合計をインスタンスで持つ形を勧める。
- 単価が 2027年1月1日に上がる(生成のモデルは2倍)ので、上限は円ではなくトークン数でも持っておく。
- 生徒に見える文は仮(心理士さんの確認待ち)。止める・すすめる判断は、敷居を下げる目的(CLAUDE.md 1節)とぶつかるので、人が決める。
