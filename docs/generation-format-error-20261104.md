# 生成の失敗(応答形式エラー)の調査と対策 — 第1部〜第3部の報告

2026年11月4日。版 `2026-11-04a`。指示書「生成エラー(応答形式エラー)の調査と対策」の第1部〜第3部と5章。第4部(危機の場面)は対象外で、
本人の危機の生成に失敗したときの固定の文と窓口のカードは今までどおり。

## 0. まとめ

- **原因(見立て)**: 「応答をJSONとして読み取れませんでした」は、AI の出力に `{` か `}` が1つも無いときだけ出るエラーだった
  (`parseJSON` は最初の `{` から最後の `}` までを読む)。返事は `{"reply":"…` で始まるので、ふつうに崩れたなら `{` は残る。
  **`}` が無い = 返事の途中で出力が切れた**、と考えるのがいちばん自然。切れる理由は、出力の上限(`MAX_TOKENS`)か、安全フィルターの途中停止(`SAFETY`)。
  以前は `readGemini` が、本文が空でないかぎり終わった理由(`finishReason`)を見ていなかったので、どちらかを確かめる手段が無かった。
  **この版から、失敗のたびに終わった理由と AI が返した出力そのものを記録する**ので、本番で次に起きたときに確かめられる。
- **手元では再現できなかった**: これまでの無料枠の再生(7ファイル・会話 484・失敗 634ターン)の失敗は、429 が 559、テスト用キーの不備(400)が 69、
  503 が 5、**形の崩れは 1**(危機のあと)だけだった。本番で起きている形の崩れは課金のキーと 3.8-flash の組み合わせで、無料枠では 429 に埋もれる。
  今日は無料枠の1日の上限も尽きていて(日本時間17時ごろに戻る)、新しい実測はできていない。
- **入れた対策**: 記録(第1部)/ 形の崩れはその場で2回まで作り直す・長さの上限で切れたら上限を広げる・返事の欄が閉じていれば返事だけ取り出す(第2部)/
  それでも失敗したら固定の一言を出さず、画面が時間をおいて作り直す(第3部)。

## 1. 第1部 記録

失敗した生成の呼び出しごとに、次を `messages.failure`(`db/schema.sql` 18節。JSON の配列)に残す。**AI の出力そのものを含むので、管理画面(合言葉で守る)だけで見る**。
生徒の画面には返さない(開発用の表示 `DEV_PANEL=on` のときだけ、そのターンの応答に含める)。

| 項目 | 中身 |
|---|---|
| stage | 何回目の呼び出しか(first / retry1 / retry2) |
| kind | 失敗の種類(形の崩れ・長さの上限・安全フィルター・利用上限(429)・混雑(503)・時間切れ・そのほか。`src/generate.mjs` の `failureKindOf`) |
| model / finishReason | 返事をしたモデル・終わった理由(STOP / MAX_TOKENS / SAFETY など) |
| promptTokens / outputTokens / thoughtsTokens | 入力・出力・考える分のトークン |
| maxOutputTokens / thinkingBudget / schemaForced | 出力の上限・考える分の上限・形(responseSchema)を強制したか(生成では今は強制していない) |
| raw / rawLength | AI が返した出力(3000字まで)と長さ |
| scene | 場面(crisisTurn・crisisGeneration・afterCrisis・thirdParty・tierB・intake・phase2) |

- 作り直しを待った失敗は**生徒の発言の行**に、作り直して通った・返事を取り出した失敗は **AI の返事の行**に付く。
- 印(`messages.flags`)にも「生成の失敗の内訳: 種類(場面・作り直しを待つ)」を残す(18節が未実行でも残る)。
- 管理画面: 会話の詳細に「生成の失敗の記録(管理画面だけ)」を折りたたみで出す。一覧の上のモデルの状態の1行に「作り直し待ち」と「失敗の内訳」(種類ごとの数)を足した。
- 集計: `node scripts/analyze-generation-failures.mjs <再生の .jsonl>...`(保留セットのファイルは読まない)。

### これまでの記録の内訳(`docs/test-results/generation-failures-20261104-summary.txt`)

無料枠の再生(2026年10月14日〜11月2日。合成の台本と、開発メンバーが試した相談のログの再生)。新しい記録が無いので、印から種類を推定した。

| 種類 | 回数 | 場面 |
|---|---|---|
| 利用上限(429) | 559 | 危機のあと 216・通常 215・気がかり 85・危機の状態の生成 43 |
| そのほか(テスト用キーがプレビュー版のモデルで 400) | 69 | 危機のあと 42・気がかり 24・危機の状態の生成 3 |
| 混雑(503) | 5 | 危機のあと 4・気がかり 1 |
| 形の崩れ | 1 | 危機のあと 1 |

場面では「危機のあと」が多いが、これは再生の台本に危機のあとのターンが多いからで、429 の比率はどの場面でもほぼ同じ。
**形の崩れが危機のあとに偏るかどうかは、この数では言えない**(1回だけ)。

### 危機のあとの指示の長さ

`AFTER_CRISIS_BLOCK_PROVISIONAL` は 984字(本人の危機の生成の指示 `CRISIS_GENERATION_BLOCK_PROVISIONAL` は 570字)。システムの指示全体から見ると一部で、
入力が長いことは出力の上限(1500)を食わないので、**入力の長さが形の崩れの直接の原因になる筋は弱い**。ただし危機のあとは「返事+問い」の形を
いくつもの決まりで縛るので、モデルが考える分(thinking)を使いやすい場面ではある。3.8-flash・3.7-flash が `thinkingBudget: 0` を守るかは、503 のため
確かめられていない(3.6-flash は守った)。考える分が出力の枠を食えば `MAX_TOKENS` で返事の途中で切れるので、記録の `thoughtsTokens` と `finishReason` で確かめる。
**指示を短くするのは、記録で原因を確かめてから**にした(短くすると安全の決まりが弱くなる。費用の対策とも重なるので、トークンの測定の結果と合わせて決める)。

### 費用の対策との関係

- 作り直しは費用が増える(1ターンで最大3回の呼び出し)。ただし形の崩れはまれで、増えるのは失敗したターンだけ。
- 画面からの作り直し(第3部)は、1回ごとに分類器を通さない(作り直しでは判定・記録・通知をし直さない)ので、生成の1回分だけ増える。
- 出力の上限を広げるのは、長さの上限で切れた作り直しのときだけ(1500 → 3000)。ふだんの上限は変えていない。

## 2. 第2部 対策

- **形の崩れは、待たずに同じモデルの並びで2回まで作り直す**(出力の揺れなので)。429・503・時間切れは、以前と同じく3秒待って、失敗したモデルを外して1回。
  ここまでに20秒を超えたら作り直さない(画面が時間をおいて作り直す)。
- **長さの上限(MAX_TOKENS)で切れたら、作り直しで出力の上限を2倍(3000まで)にする。**
- **返事の欄(`"reply":"…"`)が最後まで閉じていれば、その文だけを使う**(`src/classify.mjs` の `salvageReply`)。ほかの項目(重心・見立て等)は前のターンのまま。
  記録に「記録のみ:形の崩れた出力から返事だけを取り出した」。返事の途中で切れていれば取り出さない(途中の文は出さない)。取り出した返事も出力チェックは通す。
- **形(responseSchema)の強制はまだ入れていない**: 生成の出力は項目が多く(インテーク・まとめ・見立て等)、スキーマに無い項目は Google 側で落とされるため、
  入れるなら全部の項目を書き出す必要がある。記録で形の崩れが続くとわかったら入れる(案として残す)。

## 3. 第3部 相談者から見た動き

1. サーバの中で作り直すあいだは、入力中の表示(…)のまま(上の第2部)。
2. それでも失敗したら、**返事を保存せず**、画面に `pending_retry` を返す。画面は次の一言(仮・心理士の確認待ち。`src/notices.mjs` の `GENERATION_WAIT_NOTICE_PROVISIONAL`)を1つだけ出す:
   「ごめんね、返事を作るのに少し時間がかかってる。書いてくれたことはそのまま残っているから、少し待っててね。」
3. 画面は時間をおいて同じ発言で作り直す(`retry_seq`。発言は送り直さない)。待つ時間は 3秒・6秒・12秒…(429 は10秒から、503 は6秒から。最長60秒)。
   返事が届いたら自動で出し、一言は消す(記録には残らない)。
4. 5回試しても届かなければ「もう一度送る」のボタンを出す。押すと同じ発言で作り直す(**書き直させない**)。
5. 待つあいだも書ける。書き足したら画面は作り直しをやめ、書き足した発言の返事に、前の発言も含めて作る(サーバが続いた生徒の発言を1つにまとめる)。
   古い作り直しが遅れて届いても、返事を二重にしない(あとの発言が届いていれば `superseded`、もう返事があれば `already`)。
6. ページを閉じて開き直したとき、最後が返事のない発言なら、開いてすぐ作り直す。
7. 「でも、ここまで書いてくれたことは、ちゃんと受け取っているよ。」は使わない(場面の一言の「危機のあと」の文も差し替えた。段階ごとの応答のときだけ出る)。
8. 危機のあと・第三者の場面で失敗したときの管理画面の「確認待ち」は、最初の失敗のときだけ並べる(作り直しのたびには並べない)。職員への通知は出さない(今までどおり)。
9. **本人の危機のターン(危機の状態の生成)の失敗は、今までどおり固定の文と窓口のカード**(第4部の対象。作り直し待ちにはしない)。段階ごとの応答の流れも今までどおり。

連投(`BATCH_MODE=on`)のときも同じ(まとまりへの返事が失敗したら、まとまりの最後の発言の番号で作り直す)。
