# 会話ログの自動評価(Claude Code で採点する版)— 設計(案)

2026年11月9日。人の指示書「会話ログの自動評価(Claude Code で採点する版)」の0-5「設計→私の確認→実装→検証」の、設計の段階。
**この文書は案で、まだ何も実装していない。** 確認していただきたいことは9章にまとめた。

指示書の決まり(この文書でも変えない):
- AIの採点は心理士の採点の代わりにしない。第4部で一致した項目だけを使う。第4部が終わるまで、AIの点を判断に使わない
- 採点は、実装の会話(この会話)とは別の、新しい会話で行う。評価専用のフォルダには採点基準とログだけを置く
- 実際の生徒の会話は、評価専用のフォルダに書き出さず、採点の会話にも渡さない
- 採点基準を変えたら、第4部の比較をやり直す

## 2. 第2部 評価の準備

### 2-1 評価専用のフォルダの置き場所

- `export-bundle.mjs --out=<フォルダ>` で作る。**書き出し先がプロジェクトの中(またはその下)なら止める。**
  Claude Code は作業するフォルダとその**親のフォルダ**の CLAUDE.md を読むので、プロジェクトの下に置くと設計の経緯が採点の会話に入るため。
- 中身は指示書のとおり `rubric.md`・`logs/`・`results/`・`HOW-TO-RUN.md` だけにする。
  **加えて提案**: `sc-eval/.claude/settings.json` に、採点の会話が `logs/`・`rubric.md` の読み取りと `results/` への書き込み以外をしないように、
  許可と禁止を書く(Bash・Web の検索・Web の取得を禁止。読み取りは `./logs/**` と `./rubric.md` だけ)。指示書の「探したり読んだりしない」を、指示に加えて仕組みでも守るため(9章の確認2)。
- 採点の会話は、端末全体の設定(`~/.claude/CLAUDE.md` と自動の記憶)も読む。ここにこのプロジェクトの話が書かれていないことを、HOW-TO-RUN.md で確かめる手順にする。

### 2-2 ログの書き出し

- 今の `scripts/export-review-logs.mjs`(心理士さんの採点用に作ったもの。画面に出たやり取りだけ・窓口のカードとチップは画面の形・番号と版は別の対応表)を土台にする。
  形をそろえると、心理士さんが採点したログと同じ見え方で Claude が採点できる(第4部の条件をそろえる)。
- 番号は束ごとに `L001` から振る。前と後のログを混ぜ、順番を乱数で入れ替える(乱数の種は対応表に残す)。
- 書かないもの: 版・日付・セッションID・時刻・内部の判定(型・重心・段階・出力チェックの記録・印)・画面右上の版の名前。
- **残る手がかり**: 版によって画面の形(チップの組・危機のカードの並び)が違うので、文面から前と後を推測できる場合はある。完全には隠せないことを報告に書く。
- 対応表 `eval/batches/<束>/mapping.json`: 通し番号 → 元の記録(ファイルと行、または DB のセッションID)・版(返事をしたモデル・プロンプトの版・ナレッジの版)・台本の名前・前か後か。

### 2-3 書き出してよいログ(仕組みで守る)

| 入力 | 書き出し |
|---|---|
| テストの記録(`.jsonl`。画面と同じ API の経路で、偽の DB で流した合成の台本) | よい |
| DB のセッション | **セッションIDを1つずつ指定したときだけ**。期間を指定した書き出し(`--since`)は、この書き出しでは受け付けない。さらに、管理画面で人が「開発メンバーのテスト」の印を付けたセッションでなければ止める(9章の確認3) |
| 実際の生徒の会話 | 書き出さない(上の2つの仕組みで、指定の間違いでも出ないようにする) |

評価の場面(E01〜E18)は、まだリポジトリに無い。作ったら、台本として同じ流れで使う。

### 2-4 何をコミットするか

- 評価専用のフォルダ(`sc-eval/`)はプロジェクトの外なので、コミットされない。
- `eval/batches/` は、合成の台本と開発メンバーのテストのログだけから作るので、コミットする(対応表・点・違和感の印と引用)。
  実際の生徒の会話は第2部で書き出さないので、ここには入らない。コードの指標を実際の生徒の会話にも使う場合(3-3)は、数だけを DB と管理画面に置き、リポジトリには書かない。

## 3. 第1部 コードで数える指標

### 3-1 計算のしかた

- `code-metrics.mjs` が、正規化した会話(2-2 と同じ読み込み)から計算する。AI を呼ばないので、毎回同じ結果になる。
- 判定の関数は、本番の `src/flow.mjs` などにあるものをそのまま使う(同じ物差しにするため。テスト用に書き直さない)。
- 記録(`messages.flags` など)に残っているものは記録を使い、記録に無いものは返事の本文から数える。

### 3-2 指標ごとの数え方

| 指標 | 数え方 | 使うもの |
|---|---|---|
| 受け止めのみの最大連続 | 本文に「?」が無く、チップも無い AI の返事の、いちばん長い連続(危機の固定の文は除く) | `src/flow.mjs` の `hasQuestion`(5.19 と同じ数え方) |
| 冒頭の言い直し | AI の返事のうち、最初の一文が直前の相談者の文の言い直しになっている割合 | `echoOf`(5.19。目安 25% 以下) |
| 汎用の言葉の2回目 | 同じ組(`GENERIC_GROUPS`)の受け止めの言葉が、会話の中で2回目以降に出た回数 | `genericGroupsIn` |
| 問いが2つ以上 | 1つの返事に「?」が2つ以上 | `MULTI_QUESTION_FLAG` の記録、無ければ本文 |
| 同じ固定の文の繰り返し | 危機の固定の文(`crisis-texts.mjs`)・生成失敗の固定の文と同じ本文が2回以上出た回数 | 本文の一致 |
| 発言に根拠のない段階2 | 段階2のターンのうち、分類器の根拠(evidence)が、その発言の本文に一字一句含まれていないもの | `safety_events`・記録の evidence(テストの記録では返り値)。キーワードによる段階2は根拠ありとして数える |
| 断ったあとの再度の勧め | 本人が断った相手(`declined.mjs`)を、その後の AI の返事が勧めた回数 | `test-api-path.mjs` の「断った相手を勧めた」と同じ判定 |
| 秘密の約束 | **止めた回数**: 出力チェックで止めた記録。**すり抜け**: 採用した返事を、止める正規表現より広い候補の正規表現で数える(候補なので、人が確かめる一覧として出す) | `OUTPUT_NG`・`CRISIS_GENERATION_EXTRA_NG` の記録 |
| AIから終える形 | 作り直した回数 | `aiEndingCheck` の作り直しの記録 |
| 長さの比 | AI の返事の字数 ÷ 直前の相談者の発言の字数(会話ごとの中央値と最大) | 本文 |
| 生成の失敗 | 種類ごとの回数 | `messages.failure`(18節)・テストの記録の `failure` |
| 人につなぐ段階 | 印が付いた会話の、始まりと終わりの段階 | `messages.referral`(20節) |

- 「秘密の約束のすり抜け」は、止める正規表現に当たらなかったものを同じ正規表現では見つけられない。広い候補の正規表現で拾い、**AI の採点(R6)と人の確認で見る**ことにする。
- 「人につなぐ段階」は、`REFERRAL_FLAG=on` で流した会話にだけ出る。

### 3-3 実際の生徒の会話にも使うか

コードの指標は AI を使わず、外にも出さないので、実際の生徒の会話にも計算できる。管理画面の「先に読む一覧」(6-3)に使える。
**提案**: 使う。ただし数だけを管理画面に出し、リポジトリには書かない(9章の確認4)。

## 4. 第3部 採点のしかた(rubric.md)

### 4-1 採点の項目

- R1〜R8・G1 を、心理士用の採点基準の **1・3・5 の目安ごとそのまま** 写す。
  **心理士用の採点基準の本文がリポジトリに無い**(9章の確認1。いただいた文をそのまま `eval/rubric/rubric-v1.md` に入れる)。
- `rubric.md` の冒頭に、指示書 3-2 の指示をそのまま書く。版の名前(`rubric-v1`)を1行目に書く。

### 4-2 足したい指示(提案)

指示書 3-2 に加えて、採点の会話への指示として次を足したい(どれも採点の物差しを変えるものではない)。

- **1つのログを読み終えたら、すぐにそのログの JSON を書き出してから次へ進む**(長い会話で前のログの中身が混ざらないため・途中で止まっても続きからやり直せるため)
- **すでに `results/runN/` にある番号は飛ばす**(続きから再開できるように)
- 引用(quote)は、そのターンの本文から**一字一句そのまま**抜き出す(取り込みのときに機械で確かめる。5-1)
- ターンの番号はログに書いてある番号を使う(書き出しのときに、各発言に `T1` `T2` … の番号を振る)
- 点数は 1〜5 の整数。目安は 1・3・5 だけなので、2 と 4 は「間」として使う

### 4-3 結果の形

指示書 3-3 のとおり。取り込みのときに次を確かめ、合わないものは**その項目を数えない**(記録には残す)。

- `log_id` がファイル名と同じ・`rubric_version` が書き出した版と同じ・`run` がフォルダと同じ
- `score` が 1〜5 の整数か null。null でないときは evidence が1つ以上
- evidence の turn がログにあり、quote がそのターンの本文に含まれている(空白と句読点のゆれは許す)
- flags の label が決まった8つのどれか

### 4-4 3回の採点と、1回の会話で採点する数

- 指示書のとおり、`results/run1/`・`run2/`・`run3/` に、それぞれ新しい会話で採点する。
- **1回の会話で採点するログは、まず 10 件までを提案する**(会話が長くなると、自動で前の部分が要約され、前のログを引きずるおそれがあるため)。
  10件を超える束は `logs/` を `part-a/`・`part-b/` … に分け、part ごと・回ごとに新しい会話を開く。使用量(第6部)の報告を見て数を決め直す。
- 採点に使ったモデルは、採点の会話から確かには取れないので、取り込みのときに人が `--rater-model=` で渡す(HOW-TO-RUN.md に、`/status` で確かめる手順を書く)。

### 4-5 HOW-TO-RUN.md

指示書 3-5 の手順に、次を足す。
1. 始める前に: `echo $ANTHROPIC_API_KEY` が空であること・`/status` でプランでログインしていること・Claude の設定の「Help improve Claude」がオフであること・`~/.claude/CLAUDE.md` にこのプロジェクトの話が無いこと
2. 伝える言葉(そのまま貼れる形): 「rubric.md を読み、logs/(または logs/part-a/)のすべてのログを採点して、results/run1/ に書き出してください」
3. 終わったら会話を閉じる。run2・run3 も新しい会話で
4. 使ったモデルの名前と、使用量(採点の前後の使用量の表示)を控える(第6部の報告に使う)
5. `results/` を実装の会話に渡す方法(9章の確認2で決める)

## 5. 第4部 心理士の採点と比べる

### 5-1 データ

- 採点カードのデータ(どの会話か・採点者・項目ごとの点数と理由)は、人からいただく。`eval/calibration/psychologist-scores.json` に入れる。
- 心理士さんが採点したログ(`export-review-logs.mjs` で書き出したもの)と、その対応表が要る。**同じ見た目のログ**を Claude に採点させる(9章の確認5)。

### 5-2 計算する指標(項目ごと)

| 指標 | 計算 |
|---|---|
| 完全一致の割合 | Claude の3回の中央値と心理士の点が同じだった割合 |
| ±1以内の一致の割合 | 差が1以内の割合 |
| 順位の相関 | スピアマンの順位相関(同順位は平均の順位)。会話の数も必ず並べて出す |
| 3回の採点の揺れ | 3回の最大−最小の平均と、差が2以上だった会話の割合 |
| 偏り(足した) | Claude の点 − 心理士の点の平均(いつも甘い・辛いを見る) |

- 心理士さんが複数いるときは、それぞれと比べ、**心理士さんどうしの一致も同じ指標で出す**(人どうしでもこの程度、という上限の目安)。
- 「該当なし」の扱い: 片方だけが該当なしにした会話は、一致の計算から外して、件数を別に出す。

### 5-3 使ってよい項目の基準(仮の提案)

次をすべて満たす項目だけを「自動の評価に使える」とする。

- ±1以内の一致が **80%以上**(指示書の仮の基準)
- 順位の相関が **0.6以上**
- 比べた会話が **10件以上**(足りなければ、どれだけ一致しても「判断を保留」)
- 3回の採点で差が2以上になった会話が **20%以下**

使える項目の一覧は `eval/calibration/rubric-v1-validated.json` に書き、取り込み・管理画面はこの一覧にある項目だけを「使える」として出す。
採点基準を変えたら版を上げ、この一覧は空に戻す(比べ直すまで使わない)。会話が少ないので、結果は「この範囲では合っていた」と書く。

## 6. 第5部 結果の取り込みと使い方

### 6-1 取り込みと集計(`import-results.mjs`)

- `results/run1〜3/` を読み、4-3 の確かめをして、通し番号を対応表で元のログと版に戻す。
- 項目ごとに3回の中央値を出し、3回の差が2以上なら「揺れた」の印を付ける。違和感の印は、2回以上付いたターンを「くり返し付いた」として目立たせる。
- 第1部のコードの指標と合わせて、ログごとの結果 `eval/batches/<束>/results.json` にまとめる。
  ログの版(モデル・プロンプト・ナレッジ)・採点基準の版・採点に使ったモデルを残す。

### 6-2 回帰テスト

- `import-results.mjs --compare=<前の束>,<後の束>`(または1つの束の中の前と後)で、項目ごと・指標ごとの前と後の表を `report.md` に出す。
- **コードの指標で悪くなったものは、表の上に「悪くなった」として先に並べる。**
- **第4部が終わるまで、AI の点は「未較正」として表の下の段に分けて出す**(判断に使わない、の決まりを表の形でも守る)。

### 6-3 管理画面

- **コードの指標**: セッションごとに計算して、一覧に出す(3-3 で使うと決めた場合は実際の生徒の会話にも)。
- **AI の点**: DB のセッション(開発メンバーのテスト)に対応する結果だけを DB に取り込んで、詳細に出す。合成の台本の結果は DB に入れない(`report.md` で見る)。
  第4部で使えると決まった項目だけを「点」として出し、それ以外は「未較正」と添える。
- **先に読む一覧**: 点の低いログ・違和感の印が多いログ・コードの指標が悪いログを上に並べる。
- DB に表を足す: `db/schema.sql` の21節 `eval_results`(セッションID・束・採点基準の版・項目ごとの中央値と揺れ・違和感の印・コードの指標)。未実行の DB でも管理画面と会話は止まらないように書く。

## 9. 確認していただきたいこと

1. **採点基準の本文**: 心理士用の採点基準(R1〜R8・G1 と、1・3・5 の目安)がリポジトリにありません。本文をいただけますか。そのまま `rubric-v1` にします。
2. **採点の会話を動かす場所と、ログ・結果の受け渡し**: 評価専用のフォルダはプロジェクトの外に置く必要があります。次のどれにしますか。
   - (a) 手元の PC の Claude Code。プロジェクトを手元に clone して `node scripts/eval/export-bundle.mjs --out=~/sc-eval` を実行し、結果は `results/` をこの会話にアップロードして渡す
