# 連投と、まとめての返事(第1段階の設計)

2026年11月3日。指示書「連投機能」第1段階の設計。**確認をもらうまで実装しない。** 第2段階(うなずきの印)は、第1段階を採用してから設計する。

きっかけ: 嶋先生とのミーティング(10/14)で、若い人ほど短い文を何度も続けて送る、という意見が生徒から出た。嶋先生は、相槌を打ちながら
「ひとまとまり話してもらう」聞き方をしている(`docs/interviews/2026-10-14-shima-4-transcript.md`)。今は1通ごとに返事をするので、
吐き出している途中で毎回話が止まり、言い直しや同じ受け止めも増える。

## 0. 今の作り(変える前)

- 画面(`src/app/page.tsx`)は、送ると `chat` を1回呼び、返事が届くまで書く欄と「送る」を止める(`busy`)
- サーバ(`route.ts` の `chat`)は、1回の呼び出しで、発言の保存 → 危機の判定 → 通知・記録 → 生成 → 出力チェック → 返事と状態の保存、をまとめて行う
- 回数の上限(1時間60回。`recent_turn_count`)と「20往復」(`src/flow.mjs` の `exchanges`)は、どちらも生徒の発言の数で数えている

## 1. 全体の形

`chat` を2つに分ける。

| 呼び出し | いつ | すること |
|---|---|---|
| `post`(発言を送る) | 送るたびにすぐ | 1通を保存し、その1通の危機の判定をして、段階2なら通知と記録までする。返事は作らない |
| `reply`(返事を求める) | 1-2 の時機が来たとき | まだ返事をしていない発言のまとまりに、返事を1回作る |

- チップ・選択肢を押したとき(インテーク・危機の流れ・組G)は、今の `chat` と同じく、待たずに `post` と `reply` を続けて行う(1-7)
- 設定 `BATCH_MODE=on` のときだけ動く(既定は無効。今の `chat` のまま)。まず Preview で開発メンバーが使って秒数を調整し、採用してから本番に出す
- DB の列(下の 6章)が無いときは、設定が on でも今の動きにする(会話を止めない)

## 2. 画面(1-1・1-2)

### 2-1 書く欄と吹き出し

- AI が考えているあいだも、書く欄と「送る」は使えるままにする。チップだけは、返事を待っているあいだは押せないままにする(古いチップを押すのを防ぐ)
- 送った発言は、その場で吹き出しとして出す。サーバへの `post` は、画面の中の送信の列に入れて、**1通ずつ順番に**送る(前の `post` が終わってから次。順番が入れ替わらないため)
- `post` に失敗したら、同じ発言を同じ番号(`client_msg_id`)でやり直す(3回まで。だめなら吹き出しに「送れませんでした・もう一度送る」を出す)。サーバは同じ番号の発言を2回保存しない

### 2-2 返事をする時機(秒数はすべて仮)

画面は、最後に送った時刻・最後に書く欄に入力した時刻・まだ返事をしていない最初の発言の時刻を持ち、次のどれかが来たら `reply` を送る。

| 場面 | 時機 | 設定の名前 |
|---|---|---|
| 送ったあと、入力の気配がない | 送ってから 1.5秒 | `idle_ms` |
| 送ったあと、続けて入力している | 入力が止まってから 3秒 | `typing_ms` |
| 最初のまだ返事をしていない発言から | 最長 20秒(入力中でも返事をする) | `max_ms` |
| 段階2の危機を検知した | 入力が止まってから 1秒・最長 5秒 | `crisis_idle_ms`・`crisis_max_ms` |

- 「入力中」は、書く欄に1文字でも入っていて、最後の入力から `typing_ms` 以内のこと。書く欄を空にしたら入力中ではない。**入力中の文字はサーバに送らない**(画面の中だけで判断する)
- 段階2かどうかは、`post` の答えの `urgent: true` で知る(判定の中身は送らない。窓口のカードは返事と一緒に出る)
- 送信の列に送り終わっていない `post` があるときは、それが終わるまで `reply` を待つ(判定が終わっていない発言で返事を作らないため)
- 秒数はサーバの設定 `BATCH_TIMING`(JSON)で変えられるようにし、`start`・`resume` の答えで画面に渡す(画面に設定を埋め込まないため。秘密ではないが、`NEXT_PUBLIC_` は使わない)

### 2-3 入力中の表示(…)

- `reply` を送った時点から出す(待っているあいだに「…」を出すと、まだ書いている人をせかすため)。返事が届いたら消す
- 2-2 の時機の前は何も出さない(第2段階のうなずきの印は、ここに入る)

### 2-4 ページを閉じた・再読み込みした

- 発言は `post` の時点で保存され、判定と通知も済んでいる
- `resume` で、最後が返事のない発言なら、画面は開いてすぐ `reply` を送る

## 3. サーバ(1-3)

### 3-1 `post`

1. 字数の上限(1通 2000字)を確かめる。超えていても、今と同じく AI を使わない照合だけは通す(CLAUDE.md 5.2)
2. 発言を保存する(`client_msg_id`・`batch_id` つき。6章)。同じ `client_msg_id` があれば、保存せずに前の結果を返す
3. 危機の判定をする(4章)。結果は発言の行(`messages.safety`)に残す
4. 段階2なら通知と記録(`safety_events`)をする
5. `{ seq, urgent }` を返す

### 3-2 `reply`

画面は `{ session_id, to_seq }`(まとまりの最後の発言の番号)を送る。サーバは次の順で進める。

1. まとまり = 前の AI の返事より後の、`to_seq` までの発言。もう返事をしてあれば、その返事を返す(2回作らない)
2. まとまりの発言の判定(3-1 で残したもの)から、まとまりの段階(いちばん高いもの)・危機の種類(全部を合わせる)を決める
3. 今の `chat` と同じ流れで生成する(5章)
4. **返事と状態を保存する直前に、`to_seq` より後に新しい発言が届いていないかを確かめる**(3-3)
5. 返事と状態(重心・回数・インテークの段階・クロージング)を保存して返す

### 3-3 返事を作っている途中に新しい発言が届いたとき(提案)

| いつ届いたか | 扱い |
|---|---|
| 返事を保存する前(4 の確かめで見つかった) | 作った返事を捨てて、何も保存せずに `{ superseded: true }` を返す。画面は 2-2 の時機をやり直し、新しい発言も含めたまとまりで `reply` を送る |
| 返事を保存したあと(画面に出始めている) | 新しい発言は次のまとまりとして扱う。返事の吹き出しは最後まで出す |

- 生成を始める前にも同じ確かめをする(むだな生成を減らす)。画面は、`reply` を送ったあとに新しく送っても、その `reply` を取り消さずに答えを待つ
  (実装のときに変えた。取り消すと、サーバが保存した返事が画面に出ないまま残ることがあるため。`superseded` なら広げたまとまりで求め直し、返事が届けば出す)
- まとまりの番号(`batch_id`)は、返事を保存するときに、まとまりの最初の発言の番号にそろえる(画面が返事を待つあいだに次の番号で送った発言も、サーバがまとまりに入れたなら同じ番号にする)
- 捨てた返事は、状態を何も変えていないので、発言が失われたり、回数がずれたりしない。捨てた回数は記録して、むだになった生成の数を数える(8章)
- 段階2のまとまりでは、捨てて作り直すのは1回まで。2回目に新しい発言が来ても、作った返事を出す(危機の返事を遅らせないため)。新しい発言は次のまとまりにする
- 同じ会話で `reply` が2つ同時に走ったときは、保存の直前の確かめで、あとのほうを捨てる(前の AI の返事より後の発言が無ければ、何もしない)

## 4. 危機の判定は1通ごとにすぐ(1-4)

- キーワード・受動パターン・分類器の判定を、`post` のたびに、その1通に対して行う。返事の待ち時間には関係しない
- 分類器の「根拠は今の発言の中」(`evidenceSupportsCrisis`)は、1通ごとに当てはめる。同じまとまりの前の発言は文脈として渡す(今の「直前の会話」と同じ扱い)
- 短い返事(「うん」等)は今と同じく分類器にかけない。チップ・インテークの数字も今と同じ
- 危機の応答のあと(5.17)の判定(`CLASSIFIER_PROMPT_V2_FOLLOWUP`)への切り替えも、1通ごとに今と同じ決まりで行う
- **通知**: 段階2の発言が届くたびに `safety_events` に記録する。職員への通知は、**同じまとまりの中では最初の1回だけ**にする(提案。1つの打ち明けを5通に分けて書いた人に、通知が5回飛ばないように)。まとまりが変われば、今と同じく毎回通知する
- **固定の要素**(窓口のカード・条件つきの安全の一行)は、まとまりへの返事に1回だけ付ける。1通ごとには出さない
- 字数・回数の上限を超えた発言でも、`post` で照合と通知をする(今の `overLimitCrisisReply` と同じ考え方)

## 5. 返事の作り方(1-5)

- まとまりの発言を、順番と区切りを残したまま、1つの相談者のターンとして生成に渡す。会話の記録の中で続いている生徒の発言は、改行でつないで1つにする
  (過去のまとまりも同じ。Gemini に同じ役の発言を続けて渡さないため)
- プロンプトに次を足す:
  「相談者は短い発言を続けて送ることがある。いちばん気持ちのこもった言葉を拾って、まとまり全体に1回で応える。1通ずつ順番に答えない」
- 返事は1回。吹き出しは2つまで(今の決まりのまま)
- 冒頭の言い直しの確かめ(`echoOf`)は、まとまり全体の文と比べる
- 危機の生成の指示(5.2)・危機のあと(5.17)・断った相手(5.20)は、まとまり全体の文に当てる

## 6. 数え方と記録(1-6)

- 回数の決まり(受け止めのみは2回まで・20往復・3〜4ターンに一度のつなぎ・見立ての間隔など)は、**まとまりを1往復**として数える。
  `src/flow.mjs` の `exchanges` を「AI の返事の前に続いた生徒の発言を1つと数える」形に替える。受け止めのみの連続などは、もともと AI の返事で数えているので変わらない
- 回数の上限(1時間60回)は、**返事の数**で数える(連投で上限にすぐ当たらないため)。別に、発言の数の上限(1時間200通。仮)を置く
- DB(`db/schema.sql` 17節。新しく足す):
  - `messages.client_msg_id`(画面が付ける番号。同じ会話で同じ番号は1つだけ)
  - `messages.batch_id`(どのまとまりか。生徒の発言とそのまとまりへの AI の返事に同じ値)
  - `messages.safety`(1通ごとの判定の結果: 段階・risk・subject・種類・根拠)
  - 1通ずつの時刻は、今の `created_at` を使う
- 管理画面は、同じまとまりの発言を1つの枠にまとめて表示し、1通ずつの時刻と判定を並べる。ログの書き出し(md・txt・PDF)も同じ

## 7. インテークとチップ(1-7)

- チップ・選択肢を押したときは、待たずにすぐ `reply` まで進む(インテークの流れはコードで決めているため)
- インテークの途中に書いて連投したときは、まとまりを1つの答えとして、今の段階の答えにする(背景の問いへの答えを3通に分けた、など)
- つらさ(D1〜D5)・どうなれたらいいか(H1〜H4)は、押したときにすぐ進む
- 段階ごとの応答(`CRISIS_RESPONSE=staged`)は、チップで進む流れが1通ごとの返事を前提にしているので、**`BATCH_MODE=on` と一緒には使わない**
  (両方が設定されていたら、連投を無効にする)

## 8. 費用と速さ(1-8)

画面と同じ経路のテスト(`scripts/test-api-path.mjs`)に、連投の台本を足して、変更の前と後で次を数える。

- 1回の会話あたりの呼び出しの数(生成・分類器・作り直し・捨てた生成)
- 返事までの時間(最後の発言から返事が出るまで。画面の待ち時間と、サーバの時間を分けて)

見込み: 生成は、まとまりの数だけになるので減る。分類器は1通ごとのままなので変わらない(短い返事は今もかけていない)。
捨てた生成は、作り直しの分だけ増える(どのくらいかは測る)。

## 9. 検証(1-9)

画面と同じ経路で流す(無料枠・合成データ)。画面の時機(2-2)は、画面を動かすテスト(Playwright)で別に確かめる。

| 台本 | 確かめること |
|---|---|
| 短い文を5通続けて送る | 返事が1回だけ。5通すべてが生成に渡っている |
| 連投の途中に「死にたい」を含む | その1通の `post` で判定・記録・通知が済む。窓口のカードは返事に1回だけ。通知はまとまりで1回 |
| 1通だけ送って待つ | 約1.5秒で `reply` が送られる |
| 返事を作っている途中に追加で送る | 発言が失われない。順番が保たれる。捨てた返事の状態が残らない |
| 入力を続けて20秒を超える | 20秒で返事が出る |
| `post` をやり直す(同じ番号で2回) | 発言が1通だけ保存される |
| チップを押す | 待たずにすぐ次に進む |

そのあと、開発メンバーが Preview で吐き出す場面に使い、話しやすさと返事の長さを確かめる。最終の判断は、使った本人が読んで行う。

## 10. 変えないもの

危機の判定の中身(キーワード・受動パターン・分類器のプロンプト)、通知に相談本文を含めないこと(5.3)、画面の下の窓口の表示(どの状態でも消さない)、
危機の返事の指示と出力チェック、ログインなし。

## 11. 確かめてほしいこと

1. **通知**: 同じまとまりの中で段階2が何通あっても、職員への通知は最初の1回だけにしてよいか(記録は1通ごとに残す)
2. **作っている途中の新しい発言**(3-3): 保存前なら捨てて作り直し、保存後なら次のまとまり、でよいか。段階2のまとまりでは作り直しを1回までにすることも
3. **段階ごとの応答と一緒には使わない**(7章)でよいか
4. **回数の上限**を返事の数で数え、発言の数には別の上限(1時間200通・仮)を置く、でよいか
5. **入力中の表示(…)**を、`reply` を送った時点から出す(2-3)でよいか
